# GENESIS × FORGE — CANONICAL MASTER DIRECTIVE

**DREAM PRODUCT + ANTI-PROTOTYPE + FAIL-CLOSED ENGINEERING**

Loaded as canonical user directive on 2026-08-09.

## 0 // READ THIS FIRST

We are not trying to make another impressive prototype.

We are not trying to make another particle demo.

We are not trying to make another giant PowerShell script.

We are not trying to make something that looks amazing for five minutes, breaks on the user's actual device, and then requires 40 chat messages to repair.

We are building two connected things:

- `GENESIS = THE DREAM PRODUCT`
- `FORGE = THE ENGINEERING SYSTEM THAT MAKES GENESIS POSSIBLE AND PREVENTS IT FROM COLLAPSING INTO PROTOTYPE HELL.`

The ultimate objective is not “Generate lots of code.” It is:

- BUILD SOMETHING REAL.
- KNOW WHAT IS REAL.
- PRESERVE WHAT WORKS.
- LEARN FROM WHAT FAILS.
- NEVER CONFUSE INTENTION WITH IMPLEMENTATION.
- NEVER CONFUSE IMPLEMENTATION WITH VERIFICATION.
- KEEP MOVING TOWARD THE DREAM PRODUCT.

## 1 // WHY THIS DIRECTIVE EXISTS

Previous ambitious projects repeatedly followed this pattern:

`IDEA → EXCITING PROTOTYPE → RAPID FEATURE EXPANSION → ARCHITECTURE STRETCHED BEYOND ORIGINAL PURPOSE → PATCH → PATCH THE PATCH → LARGE SCRIPT / LARGE FILE / LARGE CHAT → ERROR → USER BECOMES TEST HARNESS → MORE PATCHES → WORKING FEATURES REGRESS → CONTEXT BECOMES ENORMOUS → NEW CHAT → PARTIAL RECONSTRUCTION → REPEAT`

This happened across simulations, games, browser experiments, GitHub Pages projects, WebAssembly experiments, PowerShell automation, launchers, NEXUS systems, Harbor systems, engine/tool experiments, local AI experiments and Windows tooling.

The problem was not lack of ambition. Invention scaled faster than architecture, verification, project memory, regression testing, recovery, diagnostics, productization, dependency management and state preservation. The new system must specifically attack these historical failure modes.

## 2 // THE PERMANENT TRUTH LADDER

Never collapse these states:

`IDEA → RESEARCHED → SPECIFIED → IMPLEMENTED → COMPILED → RUNS → TESTED → VALIDATED → DEVICE VERIFIED → REGRESSION VERIFIED → RECOVERABLE → PRODUCT`

Writing code does not prove that it works. A successful commit does not prove that it builds. A successful build does not prove that it runs. Running does not prove correctness. A screenshot does not prove simulation correctness. High FPS does not prove scientific correctness. Beautiful particles do not prove chemistry. Creature-looking objects do not prove evolution. A progress bar does not prove work is progressing. ChatGPT saying “fixed” does not prove a repair worked. Every claim must correspond to actual evidence.

## 3 // THE DREAM: GENESIS

GENESIS is a beautiful, highly interactive, multiscale scientific sandbox where complex worlds can emerge from lower-level physical and biological processes.

Long-term conceptual hierarchy:

`STAR / ENERGY SOURCE → PLANETARY ENVIRONMENT → GEOLOGY / OCEANS / ATMOSPHERE → MATTER + ENERGY → ATOMIC REPRESENTATION → MOLECULAR SYSTEMS → CHEMISTRY → SELF-ASSEMBLY → COMPARTMENTALIZATION → REPLICATION → HEREDITY → EVOLUTION → CELLS → MULTICELLULARITY → DEVELOPMENT → SENSING / SIGNALING → CONTROL → BEHAVIOR → ECOLOGY → COMPLEX ALIEN WORLDS`

GENESIS should eventually allow observation across:

`PLANET → ECOSYSTEM → POPULATION → ORGANISM → ORGAN → TISSUE → CELL → MEMBRANE / ORGANELLE → MOLECULAR SYSTEM → MOLECULE → ATOMIC REPRESENTATION`

These levels should not merely be visual skins. Where practical, state and causality should propagate between scales.

## 4 // MULTISCALE REALISM, NOT FAKE SUPERCOMPUTING

GENESIS must not claim that an iPhone is literally performing impossible all-atom simulation of an entire planet.

Instead: **MAXIMIZE CAUSAL DEPTH PER UNIT OF COMPUTE.**

Use adaptive multiresolution simulation: explicit microscopic simulation, coarse-grained molecular models, reaction networks, concentration fields, cellular models, tissue models, organism-level dynamics, population models and climate/geological fields. Different scales may use different representations. The user must be able to understand which representation is active. Never inflate particle count or graphical detail into false scientific claims.

The goal is not MOST PARTICLES. The goal is the DEEPEST CONSEQUENTIAL WORLD POSSIBLE ON AVAILABLE HARDWARE.

## 5 // EMERGENCE MUST NOT BE FAKED

Do not secretly implement `createPlant()`, `createHerbivore()` or `createPredator()` and claim those entities evolved. Do not create predefined creatures and call their appearance emergence. Do not attach a conventional AI controller to a creature and claim its behavior evolved biologically.

Desired causal direction:

`chemistry → organization → replication → variation → heredity → selection → cellular organization → development → sensing → control → behavior → ecological strategies`

Terms such as predator, prey, parasite, scavenger, producer, colony and filter feeder should ideally describe strategies observed in the resulting system rather than classes secretly assigned beforehand. When approximations are necessary, label them honestly.

## 6 // CAUSAL INSPECTION

A defining GENESIS capability is being able to ask: **WHY DID THIS HAPPEN?**

The system should increasingly preserve enough provenance to explain meaningful causal chains. The dream is not merely to WATCH emergence. It is to INSPECT emergence.

## 7 // USER EXPERIENCE

GENESIS must be fun. It should eventually support dramatic zooming across scales, touch-first inspection, beautiful rendering, atmospheric audio, responsive controls, sliders, parameter editing, experiments, destruction, environmental manipulation, mutation, chemistry manipulation, god tools, replay, branching timelines, graphs, scientific inspectors, discovery, surprising emergent behavior, creepy alien ecosystems and worlds that do not simply recreate Earth.

Engineering complexity should be hidden when unnecessary. Simulation complexity should be explorable.

## 8 // THE USER IS NOT THE TEST HARNESS

The user should not routinely have to copy giant terminal scripts, interpret stack traces, remember file paths, manually transport logs, determine compiler commands, remember which build worked, repeatedly explain architecture, rejected approaches, the GENESIS dream or old bugs.

The user is the architect/explorer. FORGE should carry the engineering burden.

## 9 // FORGE

FORGE is the development system surrounding GENESIS.

Conceptually: USER → “MAKE THIS” → FORGE → PROJECT BRAIN / WORK GRAPH / EVIDENCE.

Project Brain stores requirements, decisions, architecture, failures, history and dream contract. Work Graph handles builds, probes, diagnostics, packaging and recovery. Evidence stores tests, logs, benchmarks, screenshots, receipts and artifacts. FORGE should be internally sophisticated but externally understandable.

## 10 // PROJECT BRAIN

No critical project fact may exist solely inside ChatGPT memory.

FORGE must eventually externalize DREAM CONTRACT, REQUIREMENTS, ACCEPTED DECISIONS, ARCHITECTURE, ACTIVE WORK, LAST-KNOWN-GOOD STATE, CAPABILITY LEDGER, FAILURES, PREVIOUS FAILED APPROACHES, REPAIRS, REGRESSION TESTS, DEVICE RESULTS, PERFORMANCE BASELINES, SAVE SCHEMAS, TOOL VERSIONS, DEPENDENCIES, EXPERIMENTS, BLOCKERS, ROADMAP and HANDOFF STATE.

ChatGPT memory is helpful. It is not canonical project storage.

## 11 // PRESERVE ORIGINAL INTENT

Important user language should sometimes be preserved alongside formal engineering requirements.

Example original intent: “I want to zoom into the fucking atoms.”

Normalized requirement: GENESIS shall provide continuous-feeling multiscale navigation from macroscopic world views into microscopic/molecular representations where supported by the active simulation model.

Both are useful.

## 12 // DREAM CONTRACT

Maintain the ultimate dream separately from current implementation. For every major compromise record DREAM TARGET, CURRENT IMPLEMENTATION, APPROXIMATION, REASON, CONSEQUENCE and UNLOCK CONDITION. Do not allow temporary limitations to silently redefine the ultimate dream downward. If the dream itself changes, version it explicitly.

## 13 // PROTOTYPES ARE LABORATORIES

Prototypes are allowed. Ugly experiments are allowed. Crazy experiments are encouraged. But PROTOTYPE ≠ PRODUCT.

Every prototype eventually receives one of two outcomes: DISCARD or PRODUCTIZE. A successful experiment does not become production merely because it looks cool.

## 14 // THE PRODUCTIZATION BRIDGE

Before experimental functionality becomes part of the real product, require appropriate gates such as architecture contract → production implementation → integration → persistence → user experience → error handling → diagnostics → performance → tests → scientific/model validation → device verification → regression verification → recovery verification → VERIFIED PRODUCT CAPABILITY.

Do not skip the bridge because a prototype is exciting.

## 15 // BUILD COMPLETE PRODUCTS ALONG THE WAY

Do not require the entire atoms-to-ecosystem dream before GENESIS becomes a real product. Build increasingly deep complete products.

Possible progression: GENESIS FOUNDATION (environment, molecular/coarse chemistry, self-assembly, compartments, beautiful visualization, interaction, saves, replay, controls, iPhone support, verification), then GENESIS LIFE, then GENESIS ECOLOGY, then deeper worlds.

A smaller truthful product is superior to a giant fake universe.

## 16 // STABLE VS LAB

Once a usable Stable product exists, Stable is the last-known-good product and Labs are allowed to crash, fail, look terrible, be slow or produce bizarre output. Stable must not be casually modified. Only verified candidates are promoted.

## 17 // TINY VERIFIED INCREMENTS

Avoid giant speculative implementation jumps. Prefer ONE BOUNDED CAPABILITY → IMPLEMENT → BUILD → TEST → VERIFY → CHECKPOINT → NEXT CAPABILITY.

New ideas go to IDEA HARBOR rather than destabilizing active work.

## 18 // NO GIANT REWRITE AS DEFAULT DEBUGGING

New policy: FAILURE → CAPTURE → REPRODUCE → ISOLATE → FIND FIRST CAUSAL FAILURE → SMALLEST JUSTIFIED REPAIR → TEST → REGRESSION TEST → PROMOTE OR REJECT.

Never rewrite files that have not been inspected. Never replace working architecture without evidence.

## 19 // FAILURE KNOWLEDGE

Every meaningful failure should make future debugging cheaper. Record symptom, environment, build identity, reproduction, first causal failure, root cause, rejected repairs, successful repair, affected modules and regression test. Before proposing a solution, search structurally similar historical failures.

## 20 // CAPABILITY LEDGER

Track what actually exists, including implementation, build, platform verification, replay, science test, performance and product status. This prevents vague statements such as “GENESIS supports membranes.”

## 21 // DEBUGGING PIPELINE

FORGE should eventually automate PREFLIGHT → ENVIRONMENT VERIFY → BUILD → RUN → CAPTURE → TEST → PROFILE → COMPARE → CHECKPOINT → REPORT.

On failure, report what failed, where, first causal error, what remains safe, what was preserved, reproduction, relevant evidence and next required action.

## 22 // STOP ERROR AVALANCHES

Cluster derivative failures and identify the earliest causal blocker. Do not dump hundreds of downstream errors onto the user.

## 23 // LOADING MUST BE REAL

Never show fake progress. Loading should represent actual work units. If stalled, show the stalled operation rather than an endlessly moving spinner.

## 24 // TOOL NODE SYSTEM

FORGE should eventually expose development operations as inspectable nodes with typed inputs/outputs, versions, provenance, validation, status, evidence, diagnostics and execution history. PASS requires actual acceptance evidence; exit code 0 alone is not enough.

## 25 // NODE UX

Default view should show GOAL, STATUS, PROGRESS, FAILURE and NEXT ACTION. Advanced views can expose subsystem → workflow → nodes → execution → raw evidence. Verified boring machinery can collapse; failures and changed paths should surface.

## 26 // AUTOMATION POLICY

Automate repeated builds, environment checks, dependency verification, tests, benchmarks, regression checks, deterministic repairs, packaging, evidence collection, checkpointing, failure classification and known recovery procedures. Do not pretend deterministic automation is intelligent. Novel architecture, scientific reasoning and creative changes remain reasoning tasks.

## 27 // FREE / LOCAL-FIRST TOOLING

Required development/runtime paths should prefer free, open, local, reproducible and replaceable tooling. Do not make the project hostage to a paid service. Third-party tools require capability justification, version tracking, compatibility evidence, licensing awareness and replacement strategy.

## 28 // OFFLINE SURVIVAL

Already-built supported GENESIS functionality must be able to operate without ChatGPT. FORGE must preserve deterministic development capabilities offline. Loss of internet, ChatGPT, usage limits, subscription changes or GitHub must not make the project incomprehensible.

Novel unresolved reasoning becomes a WAITING FOR CHATGPT packet containing goal, current state, relevant requirements/files, failure, evidence, previous attempts, do-not-repeat items, acceptance criteria and next unresolved question.

## 29 // CHATGPT IS NOT A RUNTIME DEPENDENCY

Do not integrate ChatGPT as hidden intelligence controlling GENESIS. Runtime scientific behavior comes from declared simulation systems, not secret AI improvisation. Do not build a fake replacement ChatGPT just to claim autonomy.

## 30 // NEW CHAT SURVIVAL

Maintain/generate a HANDOFF PACKET before conversation complexity becomes dangerous. It should include project, stable version, candidate version, active branch, current goal, last verified capability, current failure, affected requirements, relevant architecture, previous failed approaches, relevant evidence and exact next bounded action.

## 31 // DECISION MEMORY

Accepted decisions become individual records. “D ALL” does not mean one opaque statement. Each accepted answer becomes a distinct decision/requirement with ID, statement, rationale, status, affected systems, provenance and supersession links. Conflicts must be surfaced, not silently overwritten.

## 32 // BACKUP / RECOVERY

Use layered recovery: LIVE JOURNAL → CHECKPOINTS → LAST-KNOWN-GOOD → MILESTONE ARCHIVES → RECOVERY BUNDLE. Recovery bundles should eventually preserve source, Project Brain, Dream Contract, requirements, decisions, architecture, dependencies, tool versions, build instructions, tests, known-good artifacts, save schemas, important simulation states, failure knowledge, evidence, integrity hashes and current handoff. Backups should periodically be restoration-tested.

## 33 // SAVE SYSTEM

Simulation saves must not simply serialize arbitrary runtime objects. Separate stable simulation state, transient caches, renderer resources, UI state and GPU resources. Use versioned schemas and migrations. Never destroy the only older world during migration. Support Instant, Auto, Milestone, Archive and Branch lanes as appropriate.

## 34 // DETERMINISM AND REPLAY

Where appropriate, preserve random seeds, input events, parameter changes, checkpoints and version identity to enable reproduction, debugging, comparison, branching timelines and causal analysis. Do not falsely promise bit-perfect determinism where platform/GPU numerical behavior prevents it.

## 35 // TESTING

Testing is layered according to risk: unit, property, invariant, integration, reference-model comparison, scientific validation, deterministic replay, save/load, migration, visual regression, touch interaction, device compatibility, performance, long-duration soak, fault injection, recovery, offline, fresh-chat handoff and clean-environment rebuild. Do not maximize test count for vanity.

## 36 // EVERY IMPORTANT BUG SHOULD BECOME A TEST

When practical: BUG → REPRODUCE → FIX → REGRESSION TEST → NEVER SILENTLY RETURN.

## 37 // SCIENCE VALIDATION

For scientific models, test appropriate conservation, units, stability, limiting behavior, reference cases, equilibrium/kinetics where applicable, topology/state transitions, parameter bounds and numerical convergence. Distinguish established physical model, coarse approximation, phenomenological model, speculative model and sandbox rule. Scientific uncertainty is allowed. Scientific dishonesty is not.

## 38 // ORIGIN-OF-LIFE UNCERTAINTY

Do not present one speculative origin-of-life pathway as settled fact. Where appropriate, allow competing model families with explicit assumptions, representation, parameters, limitations and validation basis.

## 39 // CPU/GPU REFERENCE PATHS

Critical optimized GPU kernels should, where feasible, have smaller trusted reference implementations or fixtures. Optimization must not silently alter model semantics.

## 40 // PERFORMANCE

Measure frame-time distributions, simulation throughput, memory, startup, loading stages, thermal/sustained behavior where possible, GPU workload, CPU workload and long-run stability. Every benchmark records device, OS/browser/runtime, build, workload, configuration, timestamp and result. Performance claims require comparable conditions.

## 41 // IPHONE IS A FIRST-CLASS TARGET

Current priority includes excellent behavior on iPhone 16 Pro Max. Account for touch, screen dimensions, Safari/WebKit behavior, WebGPU availability/behavior, memory, thermals, battery, suspension, storage, orientation, gesture conflicts and loading time. Controls should be enjoyable without keyboard/mouse. Adapt representation honestly when hardware requires lower resolution.

## 42 // PORTABILITY

Separate simulation models, state, scheduler, rendering and platform integration so stronger future targets can reuse the core concepts and data. The browser/iPhone version should remain a legitimate product in its own right.

## 43 // ARCHITECTURE

Prefer modular architecture with explicit subsystem ownership. Avoid one giant file, global mutable state everywhere, hidden cross-module mutation, architecture-by-copy-paste, accidental dependency cycles and mega-script orchestration. Potential responsibilities include scheduler, spatial world, fields, chemistry, molecular structures, membranes, cells, lineage, development, organisms, ecology, environment, persistence, replay, rendering, audio, interaction, inspectors and diagnostics.

## 44 // SIMULATION TRUTH IS SEPARATE FROM PRESENTATION

Rendering consumes simulation state. Rendering must not secretly become simulation logic. Sound consumes simulation/events. UI issues explicit commands. Pretty graphics are an interpretation of state, not evidence that state exists.

## 45 // LANGUAGE / ENGINE POLICY

Choose technologies by responsibility. Rust, WebAssembly, WGSL, WebGPU, JavaScript/TypeScript and native tooling may be appropriate, but every language/library adds build, interop, debugging and maintenance cost. Require a measurable capability reason. No technology worship and no rewrite-everything-in-X without evidence.

## 46 // DEPENDENCY POLICY

Reuse before rebuilding when a free, suitable, maintainable dependency exists. Evaluate capability, size, maintenance, browser/device support, license, debugging quality, offline suitability and replacement cost. Do not import enormous frameworks for trivial features and do not reject useful libraries simply because previous prototypes used them badly.

## 47 // USER CONTROLS

Separate SCIENCE PARAMETERS, PERFORMANCE PARAMETERS, PRESENTATION PARAMETERS and SANDBOX/GOD PARAMETERS. Do not mix reaction rate with graphics quality or particle caps without explanation. Parameter changes should be replayable where practical.

## 48 // EXTREME SETTINGS

Allow extreme experiments where safe, but protect engine integrity. Scientific instability and world collapse may be part of the sandbox; save corruption and unrecoverable application failure are not.

## 49 // VISUAL QUALITY

Do not settle for generic circles, glowing dots, generic grid particles, generic AI-app UI, placeholder gradients or visually identical levels. Target rich scientific visualization appropriate to scale: material response, depth, translucency, lighting, fields, membranes, fluids, molecular structures, volumetric atmosphere, environmental phenomena, organismal surfaces, damage, deformation and meaningful color mappings. Graphics must remain tied to simulation state.

## 50 // SOUND

Sound should support immersion and information through environmental ambience, scale-dependent soundscape, interaction feedback, major evolutionary events, structural failure, atmospheric events, discovery and transitions. Avoid generic annoying UI beeps.

## 51 // CREEPY ALIEN LIFE

Do not implement horror merely by adding monsters. Desired horror comes from believable alien ecology: parasitism, predation, colonial organisms, unusual reproduction, strange sensory structures, symbiosis, body invasion, environmental collapse, emergent swarm behavior and unfamiliar developmental pathways.

## 52 // FUN IS A REAL ACCEPTANCE GATE

Separate ENGINEERING ACCEPTANCE, SCIENTIFIC ACCEPTANCE and EXPERIENTIAL ACCEPTANCE. The user owns experiential acceptance. If tests pass but the user says “this is boring,” engineering may be correct while product design has failed.

## 53 // QUALITY GAUNTLET

Explicitly check against historical disappointments: generic particle soup, fake emergence, predefined creatures presented as evolved, fake/frozen loading, shallow chemistry/interaction, tiny mobile controls, desktop UI squeezed onto phone, broken touch, visual sameness, lost features, giant PowerShell blocks, repeated dependency failures, undocumented architecture changes, “works” claims without device verification, regressions hidden by new features, giant rewrites after small errors, context loss between chats, lost history and prototypes mislabeled as products.

## 54 // CHATGPT WORK RULES

Before changing substantial existing code: inspect current state; identify relevant requirements; identify last-known-good behavior; check relevant historical failures; define bounded change; define acceptance criteria; implement; build; test; compare; record evidence; promote or reject.

Never say “fixed” merely because code was generated. Use accurate status language: PROPOSED, WRITTEN, BUILT, TESTED, VERIFIED, FAILED, BLOCKED, NOT YET TESTED.

## 55 // DON'T BULLSHIT TYLER

Never exaggerate progress to maintain excitement. If only 2% exists, say 2%. If something is architecture only, say so. If untested, say so. If approximate, say so. If hardware cannot perform brute force, explain the actual representation. If an experiment failed, preserve evidence and say it failed. Truth is more valuable than hype.

## 56 // DON'T THROW AWAY CRAZY IDEAS

When a new idea would destabilize active work, put it in IDEA HARBOR with idea, intended experience, affected systems, prerequisites, possible implementation, blocker and unlock condition.

## 57 // FAILURE UNDER PRESSURE

Frustration is not a reason to abandon engineering discipline. Preserve state, identify last-known-good, isolate failure, choose shortest proven recovery, restore usable product where possible and continue investigation separately.

## 58 // PAUSE / RESUME

The project must tolerate being abandoned temporarily. A Pause Capsule preserves stable build, active branch, unfinished work, blocker, current evidence and next safe action so return after days or months does not require archaeology.

## 59 // FORGE ITSELF MUST NOT BECOME ANOTHER FAILED MEGAPROJECT

Build FORGE capability-first. First useful FORGE: project state, build, test, evidence, last-known-good, failure capture and handoff. Only then expand. Do not build a beautiful giant node editor before the development operations work.

## 60 // BOOTSTRAP PARADOX

FORGE cannot require completed FORGE to build FORGE. Bootstrap using the smallest trustworthy conventional tooling possible, then gradually move repeated verified operations into FORGE. Always preserve an understandable recovery route.

## 61 // NO MAGIC AUTONOMY CLAIMS

FORGE can autonomously perform deterministic operations such as build, test, benchmark, inspect, compare, configured bisect, replay, restore, package and known transformations. Novel reasoning may still require ChatGPT/human input. The goal is reliable automation, not fake AGI.

## 62 // EVIDENCE

Important verification should leave receipts: build receipt, test receipt, benchmark receipt, environment fingerprint, artifact hash, screenshot, simulation invariant results, device verification, save/replay comparison and recovery test. Evidence should be associated with the exact artifact it verifies.

## 63 // EXTERNAL ANCHORING

For critical milestones, preserve verification independently from transient chat output using Git history, CI, artifact hashes, immutable receipts, recovery archives and local known-good artifacts where useful. ChatGPT's description of success is never the only record.

## 64 // EVERY FIFTH VERIFIED UPDATE

After approximately every fifth verified functional increment, perform a polish/stability gate instead of blindly adding another major capability. Review UX, performance, diagnostics, code health, documentation, recovery, mobile interaction, visual consistency and accumulated technical debt.

## 65 // NO SILENT REGRESSIONS

Before promotion compare candidate against Stable. Report capabilities gained, changed and lost; performance changes; save compatibility; visual changes; scientific-model changes. If an old capability disappears, it is a regression unless explicitly approved.

## 66 // MIGRATION OVER REWRITE

If architecture needs replacement, prefer incremental migration with old/reference output compared against the new implementation. Only retire old implementation after evidence supports the new one. Full rewrites require unusually strong justification.

## 67 // CURRENT HARDWARE REALITY

Current important targets include iPhone 16 Pro Max and ASUS ROG Ally X / Windows. Do not assume workstation or supercomputer resources. Design around actual hardware while preserving architecture that can scale upward later.

## 68 // THE FIRST REAL TARGET

Do not immediately attempt the entire universe. The first product should prove that architecture can cross the prototype/product boundary.

A strong candidate is GENESIS FOUNDATION with one genuinely deep causal vertical slice such as environment → molecular/coarse chemical behavior → self-assembly → membrane/compartment formation, plus beautiful visualization, scale inspection, touch controls, sliders, save/load, replay, offline operation, diagnostics, performance adaptation, real iPhone verification, FORGE receipts and recovery. It must be worth playing with before creatures exist.

## 69 // SUCCESS CONDITION FOR THE NEW DEVELOPMENT PROCESS

The methodology earns trust when reality demonstrates failures without destroying Stable, automatic failure capture, no manual log transport, repair verification before promotion, regression catches, new-chat resume from canonical state, clean pause/resume, offline survival, successful recovery bundle restoration and a prototype crossing the productization bridge.

## 70 // PERMANENT ANTI-PROTOTYPE RULE

PROTOTYPES ARE LABORATORIES, NOT DESTINATIONS. Every successful experiment must be deliberately discarded or cross the productionization bridge. Never allow “looks cool” to become “basically finished,” “code exists” to become “feature works,” “build succeeds” to become “product works,” or “ChatGPT says it works” to become “verified.”

## 71 // PERMANENT MEMORY RULE

NO CRITICAL PROJECT FACT MAY EXIST SOLELY INSIDE CHATGPT'S MEMORY. Conversation is where Tyler and ChatGPT think together. The project itself must remember the project.

## 72 // PERMANENT USER RULE

TYLER IS NOT THE BUILD SYSTEM. TYLER IS NOT THE LOG TRANSPORT SYSTEM. TYLER IS NOT THE REGRESSION TEST SUITE. TYLER IS NOT THE PACKAGE MANAGER. TYLER IS NOT THE PROJECT DATABASE. TYLER IS THE ARCHITECT, EXPERIMENTER AND PLAYER.

## 73 // PERMANENT CHATGPT RULE

CHATGPT IS NOT THE SOURCE OF TRUTH. ChatGPT may reason, design, research, write code, diagnose, propose experiments and interpret evidence. The engineering system must independently establish whether a candidate builds, runs, passes tests, preserves behavior, satisfies declared model requirements, performs adequately, works on the target device and can be recovered. Confidence is not evidence.

## 74 // WHEN SOMETHING FAILS

Never treat failure as “we have to start over.” Treat it as OBSERVATION. Then preserve, capture, reproduce, isolate, understand, repair, verify and learn. The project should become stronger from failure.

## 75 // WHEN TYLER SAYS "MAKE IT BETTER"

Do not automatically add random features. Interpret improvement through causal depth, scientific fidelity, emergent complexity, visual richness, responsiveness, interaction, discoverability, performance, scale, novelty, stability and user agency. Determine which dimension needs improvement, then make the smallest architectural change capable of producing meaningful improvement.

## 76 // WHEN TYLER SAYS "D ALL"

“D ALL” means detailed D decisions from the active interview block are accepted individually. Do not compress them into “Tyler wants everything.” Preserve the actual mechanisms and constraints.

## 77 // WHAT WE LEARNED FROM THE INTERVIEWS

Tyler wants DEPTH not fake complexity; EMERGENCE not scripted imitation; BEAUTY tied to real state; HIGH USER AGENCY; VISIBLE CAUSE AND EFFECT; CRAZY EXPERIMENTS without destroying Stable; OFFLINE SURVIVAL; EASY CONTINUATION after ChatGPT disappears; DEVELOPMENT AUTOMATION that reduces work; FREE/local-first required tooling; REAL DEBUGGING; REAL PRODUCTIZATION; CLEAR STATUS; HONEST SCIENTIFIC CLAIMS; HIGH-END MOBILE EXPERIENCE; A PROJECT THAT REMEMBERS ITSELF; and A SYSTEM THAT LEARNS OPERATIONALLY FROM FAILURES.

Tyler does not want generic particle demos, shallow fake chemistry, fake emergence, generic app-builder aesthetics, giant fragile PowerShell scripts, endless setup, manual error transport, repeated forgotten decisions, huge rewrites, lost features, fake progress, fake completion or another abandoned prototype.

## 78 // THE ACTUAL DREAM

Create a world whose complexity the user can descend into. Watch matter organize. Watch structures form. Watch chemistry create opportunities for organization. Watch selection reshape those systems. Watch cells become increasingly strange. Watch ecosystems appear that nobody explicitly authored. Zoom into them. Touch them. Cut them apart. Change their atmosphere, temperature, chemistry and gravity. Poison an ocean. Create a new environment. Rewind. Branch the timeline. Watch consequences propagate. Ask why something happened and follow the answer downward through the causal hierarchy. Make the world beautiful enough that observing it is compelling, and strange enough that the user sometimes thinks “WHAT THE FUCK DID THIS WORLD JUST MAKE?” Make the engineering reliable enough that the answer is not “nothing, because the build broke again.”

## 79 // FINAL ENGINEERING PHILOSOPHY

We previously tried to scale invention faster than engineering discipline. Do the opposite now. Build the shipyard, then increasingly extraordinary ships. Every layer of complexity must increase capability, depth, reliability, observability, recoverability or user value. Complexity that only makes development harder is technical debt. Complexity that makes the simulated world deeper is potentially the product.

## 80 // FINAL DIRECTIVE

DO NOT MAKE THE BIGGEST PROTOTYPE WE HAVE EVER MADE. MAKE THE FIRST PRODUCT WE CAN KEEP. Then make it deeper, stranger, larger, more beautiful and more scientifically powerful while preserving every verified step underneath it.

Desired future: today one verified deep system; then several interacting verified systems; then chemistry that produces surprising organization; then increasingly life-like systems; then evolution; then complex organisms; then ecosystems; then alien worlds. Not because ChatGPT generated the whole universe in one response, but because GENESIS accumulated verified causal depth without repeatedly destroying itself.

## 81 // STARTING PROTOCOL

Whenever this directive is loaded into a future development session, first determine:

1. What canonical project state exists?
2. What is the last-known-good artifact?
3. What is actually verified?
4. What is merely planned?
5. What is the active bounded objective?
6. What historical failures are relevant?
7. What acceptance criteria prove the next increment?
8. What is the smallest useful implementation?
9. How will failure be captured?
10. How will Stable be protected?

If canonical state exists, continue from it. Do not reconstruct from assumptions. If canonical state does not exist, first bootstrap the minimum viable FORGE foundation—not the universe, giant node editor or 100 new features.

## 82 // THE PROMISE WE DO NOT MAKE

Do not promise there will never be another bug, nothing will fail or that we can simulate literally everything. The achievable goal is stronger: failures do not erase progress; bugs become reproducible; working builds remain available; decisions do not disappear with chat context; experiments do not secretly become production; approximations are identified; verification is external to ChatGPT confidence; the project can pause/resume; the product can exist before the ultimate dream is complete; every verified increment moves toward the dream.
